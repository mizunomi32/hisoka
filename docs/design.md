# ローカル会議録音・議事録アプリ 設計

2026-10-28 · 元ドキュメント: https://claude.ai/artifact/9PgKEH96FH8BKN54Cw4zPw

## 概要と目的

MacBook Pro（Apple Silicon）上で、会議の録音・文字起こし・要約・Markdownでの保存までを、すべてローカルで完結させる個人用アプリを作る。

- 音声も文字起こしも外部サービスに送らないため、社内会議や機密性の高い会話にも使える。
- 既存環境（Ollama）を活かし、追加コストなしで動かす。
- 会議後に議事録が自動で `~/Documents/mtg/` に並ぶ状態をゴールとする。

## 要件

決定済みの仕様は以下のとおり。

| 項目 | 決定内容 |
| --- | --- |
| 対象 | オンライン会議（Zoom/Meet等）と対面会議の両方 |
| 処理タイミング | 会議後に一括処理（リアルタイム表示なし） |
| 文字起こし | mlx-whisper（日本語） |
| 話者分離 | 行わない（文字起こしに話者ラベルを付けない） |
| 要約項目 | 概要、決定事項、ToDo、議題ごとの要点 |
| 要約モデル | Ollama + gemma4 E4B（`gemma4:e4b`） |
| 要約プロンプト | Markdownファイルで管理し、コード変更なしで編集できる |
| 人名・用語辞書 | 登録した表記で文字起こし・要約する |
| 過去の議事録 | 同じ会議シリーズの前回議事録を要約の文脈に使う |
| 保存先 | `~/Documents/mtg/` に要約、`~/Documents/mtg/raw/` に文字起こし（どちらも Markdown、ファイル名は `YYYY-MM-DD_HHMM.md`） |
| UI | メニューバー常駐 |
| 録音データ | 文字起こし後も残す |
| 通信 | 一切なし（モデル初回ダウンロードを除く） |

## 全体アーキテクチャ

メニューバーから録音を止めると、文字起こしから Markdown の保存までがバックグラウンドで順に自動実行される。

```mermaid
flowchart LR
    UI[メニューバー UI] --> REC[録音]
    REC --> ASR[文字起こし]
    ASR --> SUM[要約]
    SUM --> OUT[Markdown 出力]
```

技術スタックは Python、sounddevice、mlx-whisper、Ollama、rumps。話者分離は行わない（sherpa-onnx で試作したが、2026-10-29 にパイプラインから外した。試作のコードは Git の履歴に残っている）。

## コンポーネント設計

各処理は独立したモジュールにし、パイプラインとして順に実行する。途中の成果物はファイルに残し、どの段からでも再実行できるようにする。

### 1. 録音

- ライブラリ：sounddevice で録音し、標準ライブラリの wave で WAV（16kHz・モノラル・16bit）に書き出す。録音しながら少しずつ書くので、長い会議でもメモリを使わない。
- 録音を始めると `meetings/YYYY-MM-DD_HHMM/` を作る。Ctrl+C または SIGTERM で止め、続けて文字起こし以降を実行する。
- オンライン会議：BlackHole 2ch を入れ、macOS の「Audio MIDI 設定」で集約デバイス（マイク + BlackHole）を作って録音する。相手の音声を録る方法として BlackHole を使うことは 2026-10-29 に確定。
- 対面会議：内蔵マイクをそのまま使う。
- 複数チャンネルの入力（集約デバイスなど）は、各チャンネルを平均してモノラルにする。
- CLI では入力デバイスを `--device` で名前の一部を指定する。メニューバー化のときに「オンライン」「対面」のプリセットにする。

### 2. 文字起こし

- mlx-whisper、モデルは whisper-large-v3-turbo、`language="ja"` を固定。
- 出力はタイムスタンプ付きセグメント（start / end / text）。
- 繰り返しのハルシネーション対策に `condition_on_previous_text=False` を使う。

### 3. 要約

- Ollama の `/api/chat` を呼び、gemma4 E4B（`gemma4:e4b`）で要約する（思考モードはオフ）。
- システムプロンプトは Markdown ファイルで管理し、実行時に読み込む。コードを触らずに、要約の観点や出力形式を変えられる。
- プロンプトはチャンク要約用（map）と統合用（reduce）の2ファイルに分ける。
- 長い会議は文字数でチャンク分割し、チャンクごとに要約したうえで統合する2段構成（map-reduce）。
- 入力は文字起こしを `[00:12:34] 発言` の行にしたもの。
- 出力はJSON（概要・決定事項・ToDo・議題ごとの要点）で受け取り、Markdownに整形する。

### 4. Markdown 出力

- 要約を `~/Documents/mtg/YYYY-MM-DD_HHMM.md`、文字起こしを `~/Documents/mtg/raw/YYYY-MM-DD_HHMM.md` に書き出す。要約から文字起こしへリンクを張る。
- 日時は会議フォルダ名 `YYYY-MM-DD_HHMM` から取る。取れなければ audio.wav の更新日時を使う。
- 同じ名前のファイルがあれば `-2`、`-3` … を付け、上書きしない。
- frontmatter に日付・会議種別・音声ファイルへのパスを入れる。

### 5. メニューバー UI

- rumps で常駐アプリにする。メニューは「録音開始/停止」「入力プリセット」「処理状況」「保存フォルダを開く」「設定」。
- 録音停止後は、バックグラウンドで処理を順に実行し、完了時に macOS の通知を出す。
- 初版はターミナルから起動し、安定したら py2app でアプリ化する。

### 6. 人名・用語辞書

- 人名と用語を `~/Documents/mtg/_dictionary/` の Markdown（`people.md`、`terms.md`）に表で登録する。ファイルがなければ、読み込み時に空の表のテンプレートを作る。
- 列は「表記」「読み・誤認識されやすい表記」「補足（所属や意味）」の3つ。
- 辞書は2か所で使う。
    1. 後処理：文字起こしを読み込むとき（`load_lines`）に、誤認識されやすい表記を正しい表記に置換する。`transcript.json` は Whisper の出力のまま残すので、辞書を直せば文字起こしをやり直さずに反映される。
    2. 要約：辞書の表記を要約プロンプトに差し込み、人名や用語の表記を揃える。
- mlx-whisper の `initial_prompt` は使わない。`condition_on_previous_text=False` では最初の30秒の区間にしか効かないため。

### 7. 過去議事録の参照

- 会議に「シリーズ」（例：週次定例）を付け、frontmatter の `series` で管理する。録音開始時にメニューから選ぶ。
- 同じシリーズの直近の議事録から、決定事項と ToDo だけを抜き出して統合用（reduce）プロンプトに渡す。
- これで、前回 ToDo の進捗や決定事項の変更を要約に反映できる。文字起こし全文は渡さず、コンテキストを節約する。
- 新しい要約には前回の要約へのリンク（`[前回](2026-10-21_1400.md)` の形）を入れる。

## データとファイル構成

会議ごとに1フォルダを作り、各段の中間成果物を残す。`~/Documents/mtg/` には最終的な Markdown だけを書き出す。

```
~/MeetingRecorder/
  config.toml              # 保存先、モデル名、プリセット等
  prompts/
    summarize_chunk.md     # チャンク要約用システムプロンプト（map）
    summarize_merge.md     # 統合用システムプロンプト（reduce）
  meetings/
    2026-10-28_1400/
      audio.wav            # 録音（保持）
      transcript.json      # Whisperセグメント
      summary.json         # 要約（構造化）

~/Documents/mtg/
  2026-10-28_1400.md       # 要約
  raw/
    2026-10-28_1400.md     # 文字起こし
  _dictionary/
    people.md              # 人名辞書
    terms.md               # 用語辞書
```

要約ファイルのテンプレート：

```markdown
---
date: 2026-10-28 14:00
type: online
series: 週次定例
prev: 2026-10-21_1400.md
audio: ~/MeetingRecorder/meetings/2026-10-28_1400/audio.wav
tags: [meeting]
---
# 会議メモ 2026-10-28 14:00

文字起こし：[raw/2026-10-28_1400.md](raw/2026-10-28_1400.md)

## 概要
## 決定事項
## ToDo
- [ ] 担当：〜 / 期限：〜
## 前回からの進捗
## 議題ごとの要点
```

文字起こしファイルは見出しのあと、`[00:00:12] 〜` の行を1行ずつ段落にして並べる。

辞書ファイルの例（terms.md）：

```markdown
| 表記 | 読み・誤認識 | 補足 |
| --- | --- | --- |
| Redash | リダッシュ, レダッシュ | BIツール |
| povo | ポヴォ, ポボ | 通信サービス |
```

## リソースと処理時間の見積もり

各モデルは順番にロード・解放するため、同時に載るのは1つだけ。要約モデルが動く環境ならメモリは足りる見込み。

| 処理 | メモリ目安 | 60分会議の処理時間目安 |
| --- | --- | --- |
| 文字起こし（large-v3-turbo） | 実測 約1.5GB | 実測 約2分（39分の音声で134秒、約17倍速） |
| 要約（gemma4 E4B） | 約10GB（モデル9.5GB） | 実測 約1.5分（39分の会議で95秒、4チャンク + 統合、1回約20秒） |

要約は当初 qwen3.5 9B で試し、39分の会議で約14分かかった（出力が止まらず上限の4,096トークンまで生成した呼び出しが1回あり、約6分を占めた）。2026-10-29 に gemma4 E4B に切り替えた。

「実測」以外の数値は概算で、機種によって変わる。プロトタイプで実測して、この表を更新する。実測は Apple Silicon・メモリ24GB の MacBook Pro（2026-10-29）、初回のモデルダウンロード（約1.6GB）を除く。音声は16kHz・モノラルのWAVで1時間あたり約115MB。

## リスクと対策

最大のリスクは要約の品質と処理時間で、実際の会議音声で検証する。

| リスク | 影響 | 対策 |
| --- | --- | --- |
| 話者を区別しない | 誰の発言か・ToDo の担当者が分かりにくい | 発言中に出た名前だけを担当者にし、分からなければ「不明」とする |
| Whisperが無音区間で同じ文を繰り返す | 文字起こしにノイズが入る | `condition_on_previous_text=False`、VADで無音区間を除外 |
| 長い会議で要約の情報が抜ける | 決定事項・ToDoの漏れ | map-reduce要約、決定事項とToDoはチャンク単位で抽出してから統合 |
| 9Bモデルの要約品質が不足する | 要約が浅くなる | プロンプト調整、必要に応じて大きいモデルへの差し替えを設定で可能にする |
| BlackHole使用時にMacの音量キーが効かない | 使い勝手の低下 | 会議時だけ出力デバイスを切り替える手順を用意する |
| py2app化でマイク権限が取れない | アプリ化で詰まる | 初版はターミナル起動、Info.plistに権限の説明文を入れる |

## 開発ステップ

リスクの高い処理部分を先に検証し、録音とUIは後から足す。

1. 録音済みの音声ファイルで文字起こしを検証する（精度と処理時間を実測）。
2. 要約を追加し、プロンプトと出力形式を調整する。
3. Markdownへの書き出しを追加し、ファイル入力からノート生成までをCLIで通す。
4. 録音機能を追加する（対面→オンラインの順）。
5. rumpsでメニューバー化し、バックグラウンド処理と完了通知を入れる。
6. py2appでアプリ化する。
